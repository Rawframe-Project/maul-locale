# Checks

What verifies a change, locally and in CI, and the time each may take.

## Locally

`tools/check.sh` runs the checks in three tiers; each includes the one before it. Its builds are the CI cells' presets from `CMakePresets.json`.

| Tier | Runs | Budget |
|---|---|---|
| `changed` | The source, module, length, API documentation and snippet rules, test hygiene, the data format's layout hashes, the organization's documentation check, `clang-format` on the changed C files, and the `linux-clang-20-asan` preset (assertions on) with the CTest labels the changed files reach. | under 2 minutes on a built tree |
| `pr` | Every rule on every file, the tables generated from data in the repository, clang-tidy, the `linux-gcc-14` and `linux-clang-20-asan` presets, and 10 seconds of fuzzing per target. | under 10 minutes |
| `full` | Also the shared library with the package test and Clang Release, 60 seconds per fuzz target, `src/generated/` regenerated from the pinned CLDR and tzdb, every check against those releases (`tools/check_cldr.sh`), and the Hanja finals against Unihan. The releases are fetched into `out/cache` once. | under 20 minutes |

Run `changed` before every push. On the shared development machine, run `pr` and `full` through the workspace's heavy-job wrapper. Builds go to `out/<preset>` and the other trees to `out/check-*`, each with its log beside it.

## In CI

`.github/workflows/ci.yml` runs on every pull request, on every push to `main` and every night. The Linux jobs run in the organization's CI image, pinned by digest, and install nothing. The ruleset requires only its `required` job, which passes when every other job passed or was skipped, and the title check.

| Job | What it guards |
|---|---|
| `changes` | Whether a pull request changes anything beyond documentation; when it does not, the jobs that build are skipped. |
| `docs` | The organization's documentation check, run from the pinned commit of `.github`: allowed files, the em dash, record numbers, page sizes, links. `tools/external/` is excluded. |
| `zizmor` | The workflows: injection, persisted credentials, permissions, unpinned actions. |
| `checks` | `clang-format`, the family's source rules, the module graph, lengths, API documentation, documentation snippets, the data format's layout hashes (`tools/check_data_format.py`), test hygiene (`tools/check_test_hygiene.py`: its self-test, the test sources, and every test of the default and shared configurations labeled), that the documentation site builds, the shortest-digits tables and the Turkish and Finnish lexicons against their generators, and clang-tidy; the clang-format and clang-tidy steps fail when they find no file, so a check never passes on nothing. It runs on documentation changes too. |
| `build` | One call of the organization's `cpp.yml` per preset: GCC 14 and Clang 20 in Release, GCC 14 on 64-bit Arm (the same image, on GitHub's Arm runner), Clang with AddressSanitizer and UBSan (each test repeated up to three times on a pull request, so a flaky one fails before it merges), the shared library with the package test, macOS and `clang-cl` on Windows. All build with warnings as errors. ccache is restored on every run and saved only from `main`. |
| `msvc-headers` | Every public header compiled by MSVC's `cl` as C17 and C++17 with `/W4 /WX`. |
| `generated` | `src/generated/` regenerated byte for byte from the pinned CLDR and tzdb by `tools/regenerate.sh`; a changed, added or left-over file fails it. |
| `cldr` | `tools/check_cldr.sh`, beside `generated`: the generator's resolution against CLDR's JSON, CLDR's conformance files, collation against CLDR's and ICU4C's tables, the zones against `zic`, `zdump` and `zoneinfo`, the date tables of ICU4C in `test/`, ICU's matcher test, and the calendar suites' full sweeps ([conformance.md](../internals/conformance.md)). Both jobs restore the releases cached by their pins; `main` saves them. |
| `calendar-sweeps` | The calendar suites' full sweeps under AddressSanitizer and UBSan with assertions on, at night and on a manual run: the `conform_calendar*` programs of the `linux-clang-20-asan` preset, about a minute. |
| `unihan` | The Hanja finals against the pinned Unihan database, an 8 MB download: on every run of `main` (each push, the night, a manual run), and on a pull request only when it changes the pin, `tools/gen_hanja_finals.py` or the generated header. |
| `fuzz` | Every fuzz target from its seeds in `test/seeds/` and, but on a pull request, its cached corpus, four at a time through the family's `tools/fuzz_target.sh`: 20 seconds each on a pull request, 60 seconds on `main` and at night. It fails when no target was built. On `main` and at night each corpus is then minimized and saved ([Fuzz corpus](#fuzz-corpus)). Each target runs with an explicit seed, written to its log. A finding prints the target, the kind and count of its findings (crash, leak, timeout, oom), the runtime error lines and the sanitizer's report, and nothing else: the input, its file name (the SHA-1 of the input) and the seed stay on the runner with the target's log, because the logs and artifacts of this repository's runs are public and a run from the committed seeds replays from its seed. The job uploads none. The reports are printed once every target has finished, so that none interleaves with another. |
| `web` | The `web` preset: the library and its tests under Emscripten, run by CTest through Node, with the same skipped-test check and failure logs as the other cells, and the size of the static library. The image has no Emscripten, so this job uses the runner and the emsdk action. |

`pr-title.yml` checks that the pull request title is a conventional commit with a scope from `AGENTS.md`, and `pr-gate.yml` closes a pull request from outside the organization unless it closes an issue labeled `accepted`. `codeql.yml` runs CodeQL on every pull request and on `main`, on the C code, built with GCC 14 (an advanced setup, since the default one builds with the runner's GCC 13), and on the workflows. `pages.yml` builds the documentation site in the CI image, which carries its Python packages, and publishes it from `main`. `scorecard.yml` grades the repository's security practices weekly for the README badge, and Dependabot proposes updates of the pinned actions once a week in one pull request.

## Tests

Each suite in `test/` is one executable, registered with CTest under its name and labeled with it, through `maul_add_test` or, for a suite with arguments or the tools' libraries, `mloc_add_test`; `tools/check.sh changed` picks suites by these labels, and configuring fails on a suite without its own. The family's `tools/check_test_hygiene.py` checks the same labels after each preset's configure in `tools/check.sh` and in the `checks` job, and refuses sleeps, wall-clock reads, retries and skips in the test sources; a use that must stay carries `// hygiene: <reason>`. The white-box suites (`WHITEBOX` in `CMakeLists.txt`) include `src/` for a data layout or validator no public call reaches, and are not built in shared builds. No test reports itself skipped; a test preset that finds no test fails, and so does a CI cell where a test is skipped or not run.

The `conform_*` programs are not tests: they read files outside the repository (CLDR's test data, the tzdb), so the `conformance` target builds them and `tools/check_cldr.sh` runs them. The `conform_calendar*` programs read no file: they are the calendar suites built again with `MLOC_CALENDAR_DENSE`, which sweeps every day, year and pair the suites sample, about five seconds in Release and a minute under ASan.

## Fuzz corpus

Each target's corpus carries over from run to run in one Actions cache entry, `fuzz-corpus-<run id>`, holding a directory per target. Every run but a pull request's restores the latest entry and adds the committed seeds, which are the floor. Runs on `main` (a push, the night, a manual run) then minimize each target's corpus into a fresh directory through `tools/fuzz_target.sh --merge`, which reruns every input and fails on a finding as a run does (libFuzzer's own merge exits 0 on a crash), swap the merged corpora in only when every merge passed, and save a new entry. A pull request's run neither restores nor saves: it starts from the committed seeds alone. A run in which a target found something saves nothing, since its corpus holds inputs near the finding. The cache is not secret, since a fork's pull request can run its own workflow and restore it, so it holds nothing the committed seeds would not lead to. A target whose minimized corpus passes 10 MB fails the step, and the corpora are not saved, so one target cannot crowd the others out of the cache. The step's summary lists each target's inputs and size.

The targets share one job, four at a time, as in `maul-unicode`. A job per target, as the organization's smaller libraries run, would mean 25 containers and 25 builds of the library per run, for corpora that are still kept and minimized separately.

## Assertions

`MLOC_ASSERT` (`src/invariant.h`) states an internal invariant: a precondition between the library's own modules or a state that cannot occur unless the library is wrong. It traps in every build without `NDEBUG`, which includes the Debug, sanitizer and fuzz builds, and compiles out of Release builds. Input from callers and data files is never asserted: it is validated and refused with a status in every build.

## Budgets

Over a budget, tests are pruned or merged before anything else is added. A suite that sweeps a range samples it, keeping the branches the full sweep reaches, and leaves the full sweep to a `conform_` program, as the calendar suites do. The pull request check takes about the time of its slowest job, `generated` or `cldr`, five to seven minutes each; the build cells take two to three minutes each, less with a warm ccache.
